# PPT 图片上传响应等待：分层定位

北京时间2026-10-25早上，用户要求继续定位浏览器约3–4秒等待的来源。只用合成文档 `9e7f6c0d-0890-4e1f-851b-8f2940fb828d`，不改基础设施配置、不重启服务、不触及用户工作文件。

## 方法

浏览器原生插图，记录CDP的发送、等待与完整POST时间。截取合成XHR请求正文，仅在进程内把相同请求传给Python；分别在应用服务器经本机Caddy HTTPS、应用服务器经SSH隧道、引擎服务器本机重放各两次。标准请求头保留上传验证所需字段；排除HTTP/2伪头，不伪造或放宽JWT/项目权限。结果必须HTTP200且响应含媒体结果，否则拒绝计入。URL、JWT、Cookie和图片正文不输出、不落盘。

原生接口本次上传的是原始图片字节，不是multipart文件正文。第一次直接读取Playwright请求body得到null；随后XHR内存记录成功。初次重放因HTTP/2伪头进入HTTP/1.1触发ValueError，修正为上传必要头白名单后实际通过；失败轮次不计成绩。

## 已通过的两种图片对照

| 调用位置 | 458088字节WebP | 499642字节PNG |
| --- | --- | --- |
| 浏览器→公网入口→Caddy→SSH→引擎（h2） | 总计9.10秒，其中发送2.12秒、等待6.98秒 | 总计2.42秒，其中发送0.82秒、等待1.60秒 |
| 应用服务器→本机Caddy HTTPS→SSH→引擎 | 总计140.47 / 122.30ms | 总计57.26 / 55.08ms |
| 应用服务器→SSH→引擎 | 总计125.26 / 123.75ms | 总计49.96 / 47.82ms |
| 引擎服务器本机→引擎 | 总计177.33 / 318.98ms | 总计10.78 / 5.18ms |

所有重放均200且返回媒体结果。WebP需要引擎转换，PNG与WebP不能跨格式直接比较CPU开销。顺序重放可能有缓存/负载差异，不是冷缓存、同一时刻的严格拆分，因此不能用相减声称Caddy精确耗时多少。不过服务器侧完整路径远低于数秒，**没有复现“引擎固定处理3–4秒”**。

现场站点文件 `/etc/caddy/sites-enabled/collabspace.caddy` 的Office路由只有普通 `reverse_proxy 127.0.0.1:3396` 及转发头，没有配置 `request_buffers`。响应标识为nginx、Via Caddy；本次没有看到Cloudflare标识头，不能据此把问题归因于Cloudflare。未修改生产日志配置、未记录用户请求正文。

## 结论与精度边界

另一次500KB PNG对照：浏览器h2总计5347.89ms（发送1863.23ms、等待3476.00ms）；同一台客户端Python HTTP/1.1请求总计3040.42 / 3070.64ms（包含新建连接/TLS的发送阶段2599.90 / 2656.62ms，随后等待440.50 / 414.00ms）。应用服务器经Caddy全路径56.55 / 53.64ms，经隧道50.22 / 48.76ms，引擎本机7.54 / 5.38ms。全部200且媒体结果有效。由此可见公网上传在非浏览器客户端也需数秒，同时不同客户端/协议把时间分配到发送/等待的方式不同；不能只凭Timing栏名判断服务器处理成本。

Python和浏览器不是相同协议/连接复用条件，而且样本按顺序执行；浏览器另一轮同图只用了2.42秒。因此不能把两者差值直接算成HTTP/2固定损耗，也没有据此禁用HTTP/2。后一轮私密证据为 `measurements-layers-default.json`。

实测瓶颈指向**测试客户端到公网入口的上传/返回链路**，而不是这次服务器端固定的数秒处理。浏览器的sendEnd标记不能证明服务器端已收齐全部图片；剩余在途数据、流控/反压及往返时间仍可能落入“等待响应”。因此原先的3–4秒不是可直接分配给CPU的时间。

还不能精确确定客户端Wi-Fi/上行、运营商路由、跨地区公网、丢包重传、HTTP/2流控中哪一个占主导。没有同时采集端到端TCP包时间、ACK/重传或另一网络/地区的对照；不能宣称已确认丢包、浏览器缺陷、服务器带宽套餐不足或已经修好这段等待。

## 复现

```powershell
$env:OFFICE_PROFILE_REPLAY='1'
$env:OFFICE_PROFILE_HTTP1='0'
$env:OFFICE_PROFILE_SIZES='large-optimized,small'
node scripts/profile-office-images.cjs measure
```

脚本 `scripts/probe-office-upload-layers.py` 使用现有私密SSH配置，仅在明确设置REPLAY时运行；不会默认对普通测量请求重放。私密证据 `measurements-layers-two-format.json` 存在 `.test-runs/ppt-image-profile/`；历史压缩对照 `measurements-exact-default.json` 保留。无需调用模型、不会发送邮件，也未修改前端应用代码。
