# ONLYOFFICE 社区版路线与源码交付准备

更新：2026-10-22。参考对话：用户提供的“解决ONLYOFFICE授权问题”（6ad91258-086c-83e8-820e-d84d86eee3d2）。已读取用户消息，助手回复未完整展开，不据此转述其许可结论。

## 已确认方向

用户倾向于提供源码以采用社区版，后续有预算再考虑商业版本。当前先进行独立开发验证，不因商业许可证尚未购买而停止技术验证。这个方向尚不等于已经完成代码权属审查、全仓许可变更或公开发布。

提供源码不是转让著作权；采用开源许可证也不是简单地把仓库设置成 public。应明确授予哪些使用、修改与再分发权利，并履行适用许可义务。

## 官方获取方式与当前验证环境

使用官方 ONLYOFFICE Docs Community / DocumentServer，官方入口：

- https://www.onlyoffice.com/open-source
- https://github.com/ONLYOFFICE/DocumentServer
- https://hub.docker.com/r/onlyoffice/documentserver

本项目隔离验证采用官方镜像，部署模板为 `deploy/collabspace/office-development.compose.yml`，通过镜像摘要固定版本，未开放生产入口。合成账号与测试文件使用 `tests/office-dev/`；这不是 CollabSpace 生产身份、租户和文件存储集成。镜像能启动、编辑器能打开，不代表多人保存或 Microsoft Office 往返验收通过。

## 发布前需要形成的可审阅交付

1. 盘点底座、当前自有修改、依赖和素材的许可证与权利来源；确认哪些代码有权采用 AGPL，列出不兼容或来源不明的部分。
2. 对实际集成方式核对适用的 AGPL 与 ONLYOFFICE 条款；依据固定引擎版本保存许可证、版权及必要声明。不能假定拆成独立容器就自动消除义务。
3. 准备与运行版本对应的源码、修改记录、构建与部署说明、依赖锁文件及用户可访问的源码入口；明确引擎源码版本与本应用集成代码的范围。
4. 在公开前检查当前树、完整 Git 历史、示例数据与证据，排除凭据、私密服务器配置、个人信息和客户文件。发现历史秘密时先撤销/轮换并选择安全的发布方式，不直接切换现有私有仓库可见性。
5. 提交明确的发布方案：源码范围、许可证文本、声明、下载/仓库位置、运行版本对应关系和剩余问题。当前不改变私有仓库可见性，不擅自重新许可第三方代码。

## 技术验证与后续商业路线

隔离阶段继续验证 Word/Excel/PowerPoint 的真实多人编辑、参与者、签名保存、回调幂等、旧会话写入拒绝与 Microsoft Office 样本往返。生产阶段仍需接入现有服务端身份、租户/资源权限、撤权和版本保存；不能直接把开发测试账号与文件桥接器发布为产品。

后续商业授权可用于新的合规发布方案，但不会自动收回此前依法授予的开源权利；升级时重新核对授权覆盖范围、并发、域名、部署实例及分发方式，不承诺购买授权即可把既有开源副本收回。
