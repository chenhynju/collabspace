# 注册—邀请—个人通知联动（待实现）

用户2026-10-23补充，优先沿用现有账号与组织模型。以下是目标契约，不是已上线声明。

1. 自主注册：组织名可选，留空建立个人空间；功能不因留空受限，资源按用户、组织和ACL受限访问。
2. 邀请已注册邮箱：个人通知中心收到邀请，展示邀请组织/邀请人/授予角色/有效期，可接受或拒绝。个人收件箱不依赖收件人已是目标组织成员。
3. 邀请未注册邮箱：邮件投递邀请链接；注册页根据服务端邀请预览预填并锁定邮箱和组织名。后端根据有效token确定组织与角色，绝不按客户端组织名称入组。
4. 注册不冒充接受：入组需明确“注册并加入”或登录后“接受邀请”；拒绝不产生目标组织成员关系。受邀账号不得因注册页面组织字段额外创建同名企业。
5. 受邀者接受/拒绝均给邀请者个人通知；通知附邀请ID、组织、实际结果、处理时间。普通个人通知与现有面向组织成员的公告、IM聊天分别建模。通知仅收件人可读/已读，不暴露企业内容，不以目标组织成员权限阻断邀请本身。
6. 状态机PENDING→ACCEPTED/DECLINED/REVOKED/EXPIRED；并发与重试使用事务/CAS、席位及角色复校和通知事件幂等。邮件/通知在业务提交后投递，有失败与重试状态，不把失败发送标成成功；界面保留过期/撤销/拒绝结果。

现状已盘点：组织公告Notice/NoticeRead、未读数与已读接口、IM聊天、邮件适配器、邀请preview/accept/revoke已有；个人定向邀请通知、拒绝状态、接受/拒绝通知邀请者、注册上下文联动、邀请邮件发送闭环缺失。邀请create当前仅返回inviteUrl，不等于真实发信。

验收必须覆盖：两个组织、不填企业自主注册、已注册站内接受/拒绝、未注册邮件注册加入、邮箱不匹配、伪造组织/角色、过期撤销、并发双处理、通知重放/仅自己可读、未加入前数据拒绝、退出/撤权后资源拒绝。真实邮件投递另行验证，console不是已投递。
